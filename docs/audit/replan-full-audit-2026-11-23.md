## Вердикт

RePlan на этом коммите — рабочий локальный планировщик с осторожной записью
канона. Канонические команды не пишут проект, пока вызывающий не выбрал
`--dry-run` или `--apply`. Режим `proposal_only` не пускает нечеловеческого
согласующего и возвращает код 3. Оборванный многофайловый коммит доигрывается
из журнала следующей заблокированной записью.

Ответ, ради которого существует продукт, на части входов неверен. Недельная
нагрузка целиком кладёт недатированный спрос в каждую запрошенную неделю и
считает неизвестный остаток нулём. Исключения доступности в capacity не
входят. Diff сценария с типом `unavailable` обнуляет ресурс на всё
сравниваемое окно, не глядя на дату исключения, и после apply этот ноль в
обычном `replan workload` не остаётся.

Рядом с этим запись статусов в OpenProject сравнивает сырое имя пакета с
семью точными парами, а отчёт дрейфа сравнивает уже свёрнутый статус.
Пакет, который дрейф считает согласованным, push при области по умолчанию
`ready_only` может запланировать к переписыванию.

Шесть находок высокого веса, одиннадцать среднего и восемь наблюдений
низкого хвоста перечислены ниже с файлами.

## Находки высокого веса

### H1. Недатированный спрос входит в каждую неделю целиком, неизвестный остаток считается нулём

Область: расчёт нагрузки.

Спецификация `docs/spec/workload-calculation.md` описывает корзину
`unscheduled` для спроса, у которого нет пригодного диапазона дат. Текст
корзины говорит, что она не даёт сделать вид, будто спроса нет. Тот же
документ в разделе MVP требует корзины day, month или named period, window и
unscheduled. Для неизвестного `remaining_amount` формула задаёт
`forecast_total = unknown` и предупреждение `remaining amount unknown`.

Код после закрытия GAP-031 делит датированное окно по рабочим дням. Для окна
без дат правило другое. Комментарий в `internal/app/demand_spread.go`
говорит, что недатированный спрос считается везде. `spanShare` в этом случае
возвращает 1:

```go
func spanShare(span demandSpan, days map[time.Weekday]bool, from, to time.Time) float64 {
    if !span.dated {
        return 1
    }
    // ... доля дней окна, попавших в запрошенный диапазон
}
```

`addDemand` умножает величины спроса на эту долю, когда у запроса есть фильтр
недели. Запрос недели A и запрос недели B каждый получают полную величину.
Сумма недель умножает одни и те же часы. Отдельной корзины `unscheduled` и
предупреждения о недатированном обязательном спросе в этом пути нет.

`RemainingAmount` в `internal/domain/types.go` — указатель. Комментарий поля
ссылается на GAP-016: явный ноль должен пережить перезапись и отличаться от
«ещё не оценивали». `HasRemaining` это различает. `Remaining` для `nil`
возвращает 0. `addDemand` берёт `demand.Remaining()` и прибавляет результат к
строке нагрузки. В `finishRows` нагрузка для перегрузки берётся из
`Reserved`, а если он равен 0 — из `Remaining`. Неизвестный остаток при нулевом
резерве даёт нулевую нагрузку и нулевую перегрузку, если capacity положительна
и плановая величина в эту ветку не подставляется.

Поиск по `internal/app/validate.go` не нашёл диагностики
`remaining amount unknown`.

Тот же спрос на дашборде читается иначе. `demandHasWorkLeft` в
`internal/app/report.go` при отсутствии оценки остатка считает, что плановый
объём ещё впереди:

```go
// demandHasWorkLeft treats a demand without a remaining estimate as not
// started: its planned amount is still ahead.
func demandHasWorkLeft(demand domain.ResourceDemand) bool {
    if !domain.DemandLoads(demand.Status) {
        return false
    }
    if demand.HasRemaining() {
        return demand.Remaining() > 0
    }
    return demand.PlannedAmount > 0
}
```

Следствие: недельный отчёт может показать спокойную строку, пока `replan next`
продолжает считать спрос открытым. Для обязательного спроса без дат каждая
просмотренная неделя показывает полный объём.

### H2. Исключения доступности не меняют недельную capacity, а diff сценария обнуляет ресурс целиком

Область: расчёт нагрузки и сценарии.

`capacityInWeek` в `internal/app/workload.go` берёт долю недельной capacity
по числу дней, которые попадают в `effective_from` / `effective_to` и в
множество рабочих дней. Множество рабочих дней строит `workingDays`: оно
запоминает имена дней из окон доступности. Комментарий функции говорит, что
ресурс без окон считается работающим каждый день. Поле `Exceptions` эта
функция не читает. Поиск `Exceptions` по `internal/app/workload.go` пустой.
Часы `start_time` и `end_time` в долю capacity тоже не входят: окно задаёт
дни, по которым размазывается спрос, а не число часов дня.

В self-плане у мейнтейнера окно понедельник–пятница, 11:00–18:00, и одно
исключение `reduced_capacity` на 2026-07-24 с причиной про блок релизного
планирования. Экспорт TaskJuggler для типов `reduced_capacity`,
`extra_capacity` и `quota_reset` увеличивает счётчик и выдаёт диагностику
`taskjuggler_availability_exceptions_not_exported`. Типы `unavailable`,
`access_closed`, `maintenance` и `manual_hold` уходят в отпуск TaskJuggler.
Ни один из этих типов не уменьшает строку `replan workload`.

Diff сценария после обычного расчёта нагрузки делает отдельный шаг. Если
среди изменений есть `add` по пути `availability.exceptions` и тип исключения
`unavailable`, ресурс попадает в множество, и `applyUnavailableResource`
ставит capacity в 0, а перегрузку равной оставшейся нагрузке:

```go
for resourceID := range scenarioUnavailableResources(scenario) {
    applyUnavailableResource(result.WorkloadAfter, resourceID)
}
```

`scenarioUnavailableResources` читает тип и идентификатор ресурса. Дату
исключения с неделей запроса она не сравнивает. Обнуление применяется к
строкам уже посчитанной недели, какой бы week ни был передан в diff.

Учебный сценарий `examples/small-team/scenarios/scenario.ivan-unavailable-week-28.yaml`
называется отсутствием Ивана на неделе 28 и содержит одну дату: 2026-07-09.
Это четверг ISO-недели 28 2026 года. Таблица в `README.md` для этого сценария
показывает capacity 32, затем 0. Код diff даёт ноль на всё окно сравнения,
включая запрос любой другой недели по тому же сценарию.

После `scenario apply` исключение оказывается в availability. Обычный
`replan workload` снова считает capacity по дням недели и эффективным датам
capacity. Обнуление живёт только в `ScenarioService.Diff`.

Спецификация `docs/spec/capacity-availability-rules.md` записывает
доступную capacity как базовую capacity плюс исключения минус резервы и
прямо говорит, что без исключений модель на реальном плане ломается почти
сразу. Расчёт нагрузки это слагаемое не реализует.

### H3. Дрейф и запись статусов OpenProject смотрят на разные имена

Область: OpenProject.

`mapOpenProjectStatus` в `internal/app/import_openproject.go` сворачивает
много имён в один tracking status. После нормализации, которая оставляет
только буквы и цифры:

| Нормализованное имя источника | Tracking status |
| --- | --- |
| `new`, `open` | `not_started` |
| `tobescheduled`, `scheduled`, `inspecification`, `specified`, `confirmed` | `ready` |
| `inprogress`, `progress`, `development`, `developing` | `in_progress` |
| `blocked`, `onhold` | `blocked` |
| `review`, `readyforreview`, `developed`, `intesting`, `tested` | `review_ready` |
| `closed`, `done`, `resolved`, `accepted` | `accepted` |
| `rejected`, `cancelled`, `canceled` | `cancelled` |

Отчёт дрейфа в `scripts/lib/check_openproject_drift.py` сравнивает
`candidate.mapped_status` с `task.tracking_status`. Если оба равны `ready`,
статусного дрейфа нет. Имя `In specification`, свёрнутое импортом в `ready`,
при tracking `ready` выглядит согласованным.

Запись статусов читает семь точных пар из
`scripts/lib/openproject_status_map.json`:

| Tracking status | Имя OpenProject |
| --- | --- |
| `not_started` | `New` |
| `ready` | `To be scheduled` |
| `in_progress` | `In progress` |
| `blocked` | `On hold` |
| `review_ready` | `Developed` |
| `accepted` | `Closed` |
| `cancelled` | `Rejected` |

`scripts/lib/push_openproject_status_drift.py` планирует действие, когда
желаемое имя непустое и не равно сырому `source_status`. Сравнение идёт по
строке имени, а не по свёрнутому tracking status. Пакет в `In specification`
при tracking `ready` получает желаемое имя `To be scheduled` и проходит этот
фильтр.

Область по умолчанию `ready_only` пропускает дальше только задачи с tracking
`ready`. Остальные получают причину `status_scope_ready_only` и в PATCH не
идут. Область по умолчанию поэтому оставляет как раз тот случай, где алиас
`ready` будет переписан в `To be scheduled`. Значение области, положенное в
`.env`, хелпер отвергает: его нужно задать в окружении процесса.

Профиль источника может содержать `status_map`. Для OpenProject эта карта
копируется в сводку снимка и в `mapOpenProjectStatus` не подставляется. У
GitHub карта профиля обязательна, и импортёр ей пользуется.

Задача self-плана `task.self.single-openproject-status-map` имеет статус
`accepted` и заголовок про одну карту статусов. Тест
`TestOpenProjectStatusMapMatchesSharedMapping` проверяет, что каждое из семи
имён JSON проходит через `mapOpenProjectStatus` в свой tracking status.
Алиасы вроде `In specification` и `Blocked` этот тест не запрещает, и запись
статусов по-прежнему требует точное имя из JSON. Расхождение, описанное выше,
остаётся при зелёном тесте семи пар.

Дополнительно каталог статусов для записи читается одним GET
`/api/v3/statuses`. Имя со следующей страницы становится
`openproject_status_missing`, и этот статус пропускается.

### H4. Постраничный импорт GitHub отправляет Bearer на URL из заголовка Link

Область: секреты HTTP.

`fetchGitHubImportDocument` собирает первую страницу задач из базового URL.
Дальше цикл подставляет в `nextURL` то, что вернул `githubNextLink` из
заголовка `Link`. `githubNextLink` возвращает содержимое угловых скобок у
первого фрагмента с `rel="next"`, без разбора схемы и хоста. Следующий
`doGitHubGET` создаёт новый запрос на этот URL и, если токен непустой,
ставит `Authorization: Bearer`.

Страницы пакетов работ OpenProject собираются функцией `openProjectPageURL`
из базового URL, смещения и размера страницы. Произвольный `Link` там не
подставляется.

Следствие: ответ API или посредника, который положил в `Link` чужой URL,
получает следующий GET уже с токеном оператора. Для `https://api.github.com`
это требует подменённого или враждебного ответа. `--base-url` задаёт
оператор, в том числе на GitHub Enterprise и на локальный тестовый сервер.
Проверка `validHTTPURL` выполняется в `replan validate`, а живой импорт
берёт флаг или профиль напрямую и допускает `http`.

Сам переход по HTTP-редиректу в клиенте Go устроен иначе: стандартный клиент
снимает `Authorization`, когда хост редиректа не совпадает с исходным.
Пагинация GitHub этим путём не пользуется. Она сама создаёт следующий запрос
и сама ставит заголовок.

### H5. Клиент OpenProject на urllib уносит Authorization на другой хост

Область: секреты HTTP.

`scripts/lib/openproject_http.py` ставит opener с
`_PermanentRedirectHandler`. Класс нужен, чтобы Python 3.10, нижняя версия
набора агента, понимал ответ 308: метод `redirect_request` подменяет код 308
на 307 и вызывает реализацию `urllib`. Остальные коды, включая 302, идут в
ту же реализацию как есть.

На Python 3.13.5 это проверено локально. Сервер на `127.0.0.1` ответил 302
с `Location` на `localhost` и другой порт. Запрос нёс учебный Bearer.
Обработчик второго сервера увидел тот же заголовок `Authorization`. Хост в
URL сменился. Значение токена в этот документ не переносится.

CI гоняет те же хелперы на Python 3.10 (`.github/workflows/ci.yml`, job
`python-minimum`). Обработчик редиректа написан именно для этой версии.

Следствие: ответ OpenProject или посредника с редиректом на другой хост
получает токен API и любой другой заголовок того же запроса, который
`urllib` копирует. Обработчик RePlan из копирования исключает только то, что
исключает стандартная библиотека. Go-клиент импорта на смене хоста заголовок
авторизации снимает, но сам запрос редиректа выполняет.

Повтор запросов в Python разрешён для GET и HEAD, для явно помеченных
идемпотентных вызовов и для PATCH, в теле которого есть `lockVersion`.
Обычный POST не повторяется. Сухой прогон части хелперов всё же делает POST
на form-документ OpenProject до ворот `REPLAN_APPLY`: создание пакета работ
и часть пути статуса. Эти вызовы помечены идемпотентными и пакет работ не
создают. PATCH, создание и удаление ресурсов при невыставленном
`REPLAN_APPLY` этот проход в хелперах не нашёл.

## Находки среднего веса

### M1. Часы окон, режим размазывания, ноль capacity и часовой пояс

`workingDays` запоминает имена дней. `capacityInWeek` делит недельную сумму
на число этих дней, либо на 7, если рабочих дней нет. Часы окна на величину
capacity не влияют.

Поле `Timing.Spread` объявлено в `internal/domain/types.go` и расчётом
нагрузки не читается. Режимы `contiguous` и `manual` из спецификации
workload в коде отсутствуют. Размазывание всегда равномерное по названным
дням, либо по всем дням окна, если рабочих дней внутри окна не оказалось.

`finishRows` выдаёт `missing_capacity`, когда capacity строки равна 0 и при
этом есть плановая, оставшаяся или зарезервированная нагрузка. Явный ноль и
отсутствующая запись capacity на этом пути выглядят одинаково. Спецификация
просит различать эти предупреждения.

`resolveStatusDate` в `internal/app/project.go` принимает дату или `today`.
Комментарий функции говорит, что неизвестный или пустой часовой пояс
подменяется локальной зоной процесса. `LoadLocation` вызывается только когда
имя пояса непустое и зона загружается. Иначе `today` форматируется из `now`
как есть. Валидация при пустом поясе проекта даёт предупреждение
`missing_project_timezone` и продолжается. Спецификация канонической модели
просит не угадывать пояс и считает timezone обязательным полем проекта.

`demandWindow` при конце раньше начала меняет границы местами. Валидация
сравнивает `earliest_start` с `latest_finish` и не сравнивает
`preferred_start` с `preferred_finish`, хотя окно спроса предпочитает
preferred-поля.

`workloadWeekRange` строит понедельник от 4 января, что для ISO-недели
верно, и принимает номер недели от 1 до 53 включительно. Год из 52 недель
получает `W53`, которая приходится на первую неделю следующего года.
Пример: `2016-W53` попадает на 2017-W01. Это наблюдение низкого хвоста по
частоте и записано здесь, потому что функция та же.

Фактическая запись без разборчивой даты в `actualIntersectsWeek` считается
пересекающей запрошенную неделю: неразобранная дата возвращает истину.

### M2. Файл привязок затирается последней записью

`write` в `scripts/lib/openproject_bindings.py` создаёт временный файл в
каталоге привязок и заменяет цель через `os.replace`. Замена одного файла
атомарна. Общей блокировки между процессами нет. `append_task_binding`,
`replace_task_binding` и `remove_task_binding` читают документ, правят список
и вызывают `write`. Два процесса, прочитавшие файл до записи друг друга,
оставляют на диске документ того, кто записал позже. Привязка первого
процесса пропадает.

Для операторского цикла это карта соответствия задач и пакетов работ.
Потерянная строка выглядит как отсутствующая привязка при следующем дрейфе.
Go-хранилище этот файл только читает и писать его отказывается. Гонка живёт
в Python-хелперах.

### M3. Запись дат обновляет lockVersion и может перезаписать чужую правку

`scripts/lib/push_openproject_date_drift.py` перед apply ещё раз читает
пакеты и сравнивает живые `startDate` и `dueDate` с тем, что было в плане
действий. Если даты уже другие, apply останавливается с
`stale_live_dates`. Если даты совпали, цикл для каждого действия снова
вызывает `get_work_package` и передаёт этот объект в
`update_work_package_dates`. Новый `lockVersion` уходит в PATCH вместе с
запланированными датами.

Окно между сверкой и этим повторным чтением, а также само повторное чтение
без повторной сверки дат, позволяют записать запланированные даты поверх
правки, которая успела случиться после снимка. Описание в
`push_openproject_description_drift.py` оставляет lock версии планирования
и на HTTP 409 пропускает пакет с признаком, что пакет изменился.

Частичный apply у дат, статусов, описаний, bootstrap, связей и вложений wiki
сообщает, что уже записано, и не откатывает OpenProject. Повторный PATCH
после таймаута, если в теле был `lockVersion`, может закончиться 409 и
кодом исхода `outcome_unknown` / `earlier_attempt_may_have_applied`.

### M4. Связи и time entries обрывают страницы раньше пакетов работ

Цикл пакетов работ в `fetchOpenProjectCollection` останавливается, когда
страница пуста или число уже собранных элементов достигло `total`.

Циклы связей и time entries останавливаются, когда страница пуста или
`offset * pageSize >= total`. `offset` здесь — номер страницы. Если сервер
вернул меньше элементов, чем запрошенный размер страницы, формула считает
диапазон закрытым и хвост не читается. Python-сборщик страниц в хелперах
ориентируется на число загруженных элементов. В журнале калибровки уже
отмечено, что ранний обрыв первой страницы связей приводил к повторному
созданию связей. Go-импорт связей на формуле `offset * pageSize` остаётся.

Оба цикла не отличают повтор одной и той же страницы. Если `total` отсутствует
и читается как 0, первой страницы достаточно, чтобы остановиться.

Снимок «raw» после живого чтения — это JSON уже разобранной структуры, а не
исходный документ API. В структуре пакета остаются идентификатор, тема,
описание, статус, исполнитель, оценка, потраченное время, начало, срок и
часть ссылок. Тип, приоритет, версия, категория, родитель, ответственный,
автор, процент выполнения, пользовательские поля, `scheduleManually`,
`ignoreNonWorkingDays`, `lockVersion` и метки времени в этот снимок не
попадают. `lag` связи разбирается и затем отбрасывается. Поддержанные типы
связей: `precedes`, `follows`, `blocks`, `blocked`, `relates`. `follows`
разворачивается в `finish_to_start`. `duplicates` даёт
`openproject_relation_type_unsupported` и пропускается. Родительская связь
в зависимость не превращается.

Оценки и потраченные часы каноническим спросом сами не становятся. Спрос
приходит из sidecar. Time entries остаются в режиме `proposal_required`, пока
нет `--accept-time-entries`. Повторный `import accept` существующей задаче
заголовок и описание из кандидата не переписывает.

Закрытые пакеты живой импорт опускает, пока не передан `--include-closed`.
Скрипт дрейфа этот флаг ставит. Ручной импорт без флага видит закрытый
привязанный пакет как отсутствующий.

`--since` для даты без времени отправляет дату. Значение RFC3339
превращается в календарную дату этого мгновения и фильтруется оператором
дат через `2099-12-31`. Время суток и пояс отдельный диапазон меток времени
не задают.

Праздники экземпляра не читаются. Читается `/api/v3/days/week`. Если вызов
не удался, суббота и воскресенье считаются нерабочими. `ignoreNonWorkingDays`
ставится в истину, когда отправляемая дата падает на нерабочий будний день,
и обратно в ложь этим путём не возвращается.

### M5. Проверка журнала смотрит на заполненность полей

`AuditService.Verify` в `internal/app/audit.go` считает запись неверной,
если пусты id, актор или операция. Коды: `missing_audit_id`,
`missing_audit_actor`, `missing_audit_operation`. Хеша предыдущей записи,
подписи и сверки с журналом коммита нет. Строка с теми же тремя полями и
другим смыслом проверку проходит.

`Store.AppendAudit` читает месячный файл целиком, дописывает JSON-строку в
памяти и записывает файл обратно через `s.fs.write`. Это не отдельный
`O_APPEND` одного дескриптора. Два писателя без внешней сериализации могут
потерять строку тем же способом, что и файл привязок. Пишущие команды CLI
держат `.replan/write.lock` до своей работы. Правка файла журнала мимо CLI
этой блокировкой не ловится: у того, кто может писать файлы проекта, и так
есть возможность заменить журнал.

`docs/security/access-and-actor-model.md`, раздел про то, что локальный CLI
обеспечивает сегодня, датированный сверкой с кодом 30 октября 2026, говорит,
что журнал append-only и проверяется `replan audit verify`. Поздний абзац
того же документа говорит, что MVP не делает корпоративную защиту от
подмены. Первая фраза шире, чем `Verify` и `AppendAudit`.

Поля `Before` и `After` у записи аудита есть. Решения по предложениям их не
заполняют. Печать калибровки проекта заполняет.

Тест `TestAuditListVerifySmallTeamFixture` проверяет счастливый путь одной
записи `create_baseline`. Отдельного теста на три кода пустых полей этот
проход не нашёл.

### M6. Ссылка дашборда экранирует текст и пропускает схему

`internal/reports/html.go` собирает ячейку OpenProject так: при пустом URL
идентификатор экранируется внутри `span`; при непустом URL тот же
`html.EscapeString` подставляется в атрибут `href`. Кавычки и угловые скобки
так ломаются. Схема `javascript:` и `data:` остаётся допустимым значением
href. Тот же приём используется для других URL отчёта, включая адрес пакета
около строки 1281.

Оверлей копирует URL в JSON. Шаблоны плагина печатают его через `h()` /
`<%= %>`. `h()` схему не отрезает. URL приходит из `links.self.href`
OpenProject или из `html_url` GitHub. Враждебный источник может положить его
в снимок, а снимок — в дашборд. Статический HTML своей Content-Security-Policy
не задаёт. Политика самого OpenProject может запретить такой URL внутри
плагина. Этот репозиторий свою политику туда не добавляет.

Текст задач экранируется. Золотые тесты HTML ловят пропавшую секцию и
неэкранированный текст фикстуры. Отдельного запрета схемы этот проход в
тесте не видел.

### M7. Читатель может увидеть смесь файлов одного коммита

Пишущая команда берёт `.replan/write.lock` до восстановления журнала и до
работы. Windows блокирует байт через `LockFileEx`, остальные системы —
`flock` на открытом дескрипторе. Читающие команды блокировку не берут.

`stagedFS.commit` заменяет файлы проекта по одному после того, как журнал
стал устойчивым. Комментарий журнала говорит, что вызывающие вне
заблокированного CLI должны сериализоваться сами. Параллельный
`replan report` может прочитать уже новый `resource_demands.yaml` вместе со
старым `tasks.yaml`.

Замена или удаление самого `write.lock`, пока держатель ещё держит старый
дескриптор, на Unix позволяет второму процессу заблокировать новый inode.
`init` специально вне этой предварительной блокировки и создаёт каталог
`.replan` исключительным `mkdir`. `project recover` доигрывает журнал с
`--apply` без нового актора и без новой записи аудита. Кто может подложить
этот журнал, тот уже может писать файлы проекта.

### M8. Снимок импорта пишется без `--apply` и без журнала коммита

Список `canonicalWriteCommands` в `cmd/replan/apply_gate.go` включает
`import accept` и не включает `import openproject` и `import github`. Эти
две команды пишут снимок, если не передан `--dry-run`. `cli.md` это
описывает. Снимок лежит под `imports/`, не под `canonical/`.

`WriteImportSnapshot` пишет `manifest.yaml`, `raw.json` и `mapped.json`
отдельными вызовами записи, не через `stagedFS.commit`. Обрыв между ними
`RecoverCommit` не чинит. Токен в манифест не кладётся: сохраняется имя
переменной окружения.

`tracking suggest --write-candidates`,
`proposal suggest-dependencies --write-candidates` и
`taskjuggler import-result --write-candidate` тоже обходят флаг `--apply`.
Их тексты говорят, что пишутся кандидаты, а не канон. Эти пути идут через
создание файлов проекта и получают журнал и блокировку. Ворота для них —
отдельный флаг записи кандидатов, а не `REPLAN_APPLY`.

Фраза security-документа «ничего не пишется без `--apply`» относится к
канону точнее, чем ко всему дереву проекта. Для снимка импорта она шире
кода.

Слой привязок в хранилище читать можно, писать из этих команд нельзя: при
активном слое каноническая запись получает `bindings_layer_read_only`.

`scripts/smoke-mvp.sh` гоняет Python-тесты, каркас плагина, загрузчик dotenv,
большой набор команд на копиях фикстур и сверяет выбранные подстроки, коды
выхода и несколько живых чисел self-плана. Он не вызывает TaskJuggler, GitHub
и живой OpenProject. Золотые файлы Go закрывают диагностику валидации, приём
импорта, страницы дашборда и часть markdown. Недельный HTML в
`internal/reports/render_test.go` проверяется по заголовку и одному
`<h2>Workload</h2>`. Пропавшая соседняя секция при сохранившейся фразе
такой проверке не мешает. Дашборд этим путём не страдает: золотой файл
сравнивает страницу целиком.

Покрытие процентом в этом аудите не считалось. Утверждения «не покрыто» ниже
относятся только к тем местам, где просмотрены сами тесты.

### M10. Приложение одно, адаптера источника нет

Цифры раздела измерений. `internal/app` держит и правила плана, и клиентов
HTTP. `internal/storage/filestore/store.go` импортирует `internal/app`.
Производственный код приложения хранилище не импортирует: зависимость
направлена от хранения к приложению.

Валидация профиля источника отвергает имя вне `openproject` и `github` кодом
`unsupported_source_profile_source`. Plane, GitLab и CSV из архитектурного
наброска в этом дереве источниками не являются. GitHub и OpenProject
заполняют общий `ImportMappedSnapshot`, и `import accept` у них общий.
Отдельных типов сервиса два. Особые ветки приёма остаются у time entries,
закрытых идентификаторов OpenProject и перевода типов связей.

`cmd/replan/main.go` на этом дереве заканчивается на 229-й строке и только
разводит команды. Инвентарь «божественных функций» в старом `main.go` к
этому коммиту устарел как карта файла. Сложность никуда не делась: она в
соседних файлах команд и в `internal/reports/html.go`. golangci-lint в этой
сессии не запускался, поэтому числовое «0 замечаний» из документа базы не
перепроверялось.

### M11. Черновик сценария применяется к текущему плану

`ScenarioService.Apply` ставит `NewStatus: "applied"` и отказывает сценарию,
который уже применён. Другого предусловия по статусу, отделяющего черновик
от просмотренного сценария, в этом пути нет. Наложение сценария не
переписывает факты и базы: обработчики изменений их не назначают.

`docs/spec/scenario-model.md` различает accept и apply и называет это
различие обязательным. `docs/spec/canonical-model.md` в списке статусов
сценария содержит `proposed` и не содержит `reviewed`.
`ValidScenarioStatus` следует каноническому списку. Спецификации между собой
расходятся, код следует канонической модели и при этом пускает в apply
статус, который ещё не отделён шагом accept.

Отмена зависимости через сценарий требует `--evidence`. Это закрытый
GAP-032, и тест `TestScenarioApplyCancelDependencyRequiresEvidence` ждёт
`evidence_required`. Это отдельное, работающее ограничение. Оно не заменяет
порог статуса сценария.

## Низкий хвост

Эти наблюдения подтверждены чтением и не получили отдельный вес выше.

1. ISO-неделя 53 принимается для любого года. См. M1 и `workloadWeekRange`.
2. Перевёрнутое окно `preferred_start` / `preferred_finish` меняется местами
   в `demandWindow`, а не отвергается валидацией.
3. Go-клиент OpenProject кладёт в текст диагностики до 4096 байт тела ответа
   или сообщение API (`openProjectHTTPStatusDiagnostic`). Python-клиент
   оставляет код и разобранное сообщение и сырое тело отбрасывает. Токен в
   снимок при этом не пишется.
4. Недельный HTML проверяется подстрокой. Дашборд, Гантт и страницы нагрузки,
   сценариев, предложений и оценок закреплены золотыми файлами
   `internal/reports/html_golden_test.go`, включая пустой проект и текст,
   который обязан быть экранирован.
5. Таблица базы lint указывает строки старого `main.go`. Функции разъехались
   по `cmd_imports.go`, `cmd_tracking.go`, `cmd_proposals.go` и соседним
   файлам. Подавление gocyclo в `wait_report.go` в списке семи рендереров не
   названо.
6. Пустой timezone проекта — предупреждение `missing_project_timezone`, работа
   продолжается. Спецификация считает поле обязательным.
7. Путь файла actuals по ISO-неделе собран дважды: `internal/app/actual.go` и
   `internal/storage/filestore/store.go`. `AuditShardPath` уже вынесен в одно
   место. Эти две функции на момент чтения совпадают.
8. `SourceStatus` описан в канонической модели как объект на задаче, который
   по умолчанию не затирает `tracking_status`. В `domain.Task` есть
   `TrackingStatus` и `SourceRefs`, отдельного объекта статуса источника нет.
   Затирания tracking статусом импорта это избегает, потому что приём импорта
   — отдельная команда. Сверки конфликтующего статуса источника в том виде,
   в каком её просит список предупреждений спецификации, хранить негде.

Дополнительно, без отдельного дефекта безопасности: идентификатор базы не
проходит отдельную проверку «безопасный сегмент пути». `CreateProjectFile`
отказывается заменить существующий файл. Импортные ключи снимка — метки
времени. YAML v3 отвергает чрезмерное разворачивание якорей после большого
коэффициента. Загрузчик не включает `KnownFields`, неизвестные ключи
молча пропускаются, и это записано в спецификации формата. TaskJuggler
запускается через `exec.CommandContext`, без оболочки. Идентификаторы в
экспорте сужаются до букв, цифр и подчёркивания. Комментарии экспорта
подставляют часть полей как есть. Новая строка в идентификаторе, который
валидация по алфавиту не режет, выходит из комментария. Это имеет значение
для проекта, который оператор уже отдал `tj3`.

В CI нет `pull_request_target` и нет `permissions: write-all`. Релизный джоб
добавляет `id-token: write` и `attestations: write` для
`actions/attest-build-provenance`. Actions приколоты к мажорным тегам, не к
дайджестам. `gem install taskjuggler` и `pip install pyyaml` в CI без пина
хеша. Это остаточный риск поставки, не инъекция в workflow.

доказательствами, предложениями и нагрузкой. Ни одна сторона не побеждает
дрейф автоматически.

## Что в коде держится

Канонические команды из списка `canonicalWriteCommands` требуют ровно один
выбор: `--dry-run` или `--apply`. Вместе они дают `apply_choice_conflict`.
Без обоих, и без `REPLAN_APPLY=1`, команда останавливается с
`apply_choice_required`. Если переданы оба флага, побеждает отказ. Если
передан только `--dry-run`, пробный прогон выполняется даже при
`REPLAN_APPLY=1`. Загрузчик dotenv в набор агента переменную `REPLAN_APPLY`
из файла не подхватывает. Это проверяет smoke по описанию скрипта. Сам smoke
здесь не запускался.

Журнал коммита пишется и сбрасывается на диск до замены файлов проекта.
Блоб сверяется по SHA-256. Неполный журнал убирается. Порченый журнал
возвращает ошибку порчи, а не молчаливую полузапись. Следующая пишущая
команда под блокировкой его доигрывает.

При опущенном блоке `ai_agents` режим мутации — `proposal_only`.
Согласующий для `proposal accept`, `proposal reject`, `scenario apply`,
`baseline create`, `estimate calibrate`, `import accept` и
`actual add-status` со статусами `accepted` и `cancelled` должен иметь
`kind: human`. Иначе диагностика `approver_not_human` и код 3, в том числе
на пробном прогоне, и запись не начинается. Проверка есть в тестах CLI.
`trust_level` по-прежнему описательный: валидация о нём предупреждает и не
режет команду.

Это граница имени актора. Документ модели доступа говорит прямо: вызывающий,
который может запустить `replan` и писать файлы, может указать человека в
`--actor`. `resource add` с человеческим классом и `--with-actor` создаёт
такого актора, потому что это не команда согласования. Граница «агент
предлагает, человек согласует» работает, когда агент не может писать от
имени человека.

Базы и калибровки запечатаны SHA-256, и печать проверяется до применения.
`CreateProjectFile` не заменяет существующий файл. Форматирование канона
отказывается от прогона, который изменил бы разобранный YAML. Сценарий не
пишет факты и базы своим наложением.

Токены читаются из окружения или из файла секрета. Профиль хранит имя
переменной. Валидация отвергает `base_url` с встроенным userinfo. Снимок
импорта токен не хранит. `private/`, `private-pilot/`, `local-pilot/` и
`.env` в `.gitignore`. Пример привязок в коммите использует учебный хост.
Этот проход живого токена и приватного базового URL в отслеживаемых хелперах,
плагинах и примерах профилей не нашёл. История git до этого коммита отдельно
не перечитывалась: журнал калибровки уже отмечает, что два коммита июля
содержали имя сервера. В этот документ они не копируются.

Повторы Go-клиента делаются только для GET и только после сетевой ошибки или
кодов 408, 429, 500, 502, 503, 504. Импорт OpenProject пакеты не изменяет.

Оверлей — страницы GET с правом `view_replan_overlay`. Поиск файла оверлея
отвергает идентификатор, который не является безопасным сегментом пути.
Страница показывается, когда `schema_version` равен 1 или 2 и
`openproject_project_id` совпадает с проектом страницы.

В каждом Go-пакете этого модуля есть тесты. Доменные тесты тонкие: 172
непустые строки против 597 строк кода. Предикаты статусов покрыты
`status_test.go`. Поведение `Remaining` для явного нуля проверяется тестами
фактов.

Утверждения `ROADMAP.md` про сериализацию записи одного проекта и про
доигрывание прерванной записи совпадают с блокировкой и журналом, с
уточнением из getting-started: доигрывает следующая пишущая команда.

## Приватность этого документа

Здесь нет живых токенов, приватных базовых URL, адресов VPS и приватных
идентификаторов пакетов работ. Учебный Bearer из пробы редиректа не
записывался. Идентификаторы задач self-плана, которые уже лежат в
`examples/replan-self`, названы только там, где они объясняют закрытую
задачу карты статусов. Числа баз и калибровок взяты из тех же публикуемых
примеров.

## Если эти находки принимаются как работа

Порядок ниже — рекомендация аудита, не согласованный бэклог. Пока оператор
её не принял, заводить пакеты работ из этого списка рано. Когда примет,
каждая нетривиальная строка идёт в цикл OpenProject и RePlan, а этот файл
остаётся объяснением, не источником задачи.

1. Свести расчёт нагрузки к одному правилу для недатированного спроса,
   неизвестного остатка и исключений доступности. Diff сценария должен
   вызывать тот же расчёт, а не обнулять ресурс после него. Сюда же относятся
   предупреждения, которые спецификация уже назвала: `unscheduled` и
   `remaining amount unknown`.
2. Одна карта статусов для импорта, дрейфа и записи. Область `ready_only`
   не должна планировать PATCH для имени, которое импорт уже счёл тем же
   tracking status. Тест семи пар это не ловит: его стоит расширить алиасами
   и сравнением «дрейф молчит, а push планирует действие».
3. Следующий URL GitHub принимать только при той же схеме и том же хосте,
   что и базовый URL. В Python-клиенте снимать `Authorization` и служебные
   заголовки периметра, когда хост редиректа другой.
4. Поправить таблицу статуса `cli.md` про `import github` и код 3, число
   задач и коэффициент в `README.md`, инвентарь getting-started и шапку
   `known-gaps.md`. Открыть в регистре то, что этот аудит подтвердил и что
   ещё не заведено как задача.
5. Общая блокировка файла привязок. Запись дат держать lock так же, как
   запись описания: конфликт 409 пропускает пакет, а не перезаписывает его
   новым lock.
6. В CI: `-race` хотя бы на одном джобе, сборка `project_lock_windows.go`,
   прогон тех тестов `tj3`, которые сейчас пропускаются, потому что бинарника
   нет на Go-джобе. Полный golangci-lint по дереву, а не только новые
   замечания, если база в документе считается закрытой.

Низкий хвост можно брать вместе с соседней работой, отдельно он очередь не
задаёт.
