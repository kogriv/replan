# Report behavior

Date: 2026-07-06

Status: approved functional design.

## Purpose

This document defines RePlan report behavior.

It answers:

- what the weekly report must show;
- what the scenario report must show;
- what machine-readable JSON must include;
- what CSV must include;
- whether static HTML is required in MVP;
- which report sections are required for human validation;
- how reports support AI-CLI-first workflows.

This document is functional design. The exact CLI and storage layout will be
defined later in `docs/spec/cli.md` and `docs/spec/storage-layout.md`.

## Core decision

Reports are a primary RePlan interface.

They are not only presentation output.

Reports are used for:

- human validation;
- AI-agent inspection;
- planning review;
- workload review;
- scenario review;
- proposal review;
- audit-friendly explanations;
- exports to simple external tools.

Approved rule:

```text
JSON = canonical machine-readable report output
Markdown = human-readable CLI/report output
CSV = tabular export for manual analysis
HTML = optional static view, not MVP core
```

## Report principles

Reports must be:

- deterministic for the same inputs;
- explicit about `status_date`;
- explicit about baseline used for comparison;
- explicit about current plan source;
- explicit about scenario used when applicable;
- clear about unknown values;
- clear about warnings;
- clear about proposals requiring decisions;
- useful to humans;
- parseable by AI-CLI agents.

Reports should not hide missing data.

If RePlan does not know capacity, dates, remaining work or actuals, the report
must show that explicitly.

## Required MVP report types

MVP should support or model:

```text
weekly_report
resource_workload_report
task_tracking_report
warnings_report
scenario_diff_report
evidence_proposals_report
```

These can initially be generated by one command with sections, or by separate
commands later.

## Common report metadata

Every report should include metadata.

Required metadata:

```yaml
report:
  type: weekly_report
  generated_at: 2026-07-06T12:00:00+07:00
  status_date: 2026-07-06
  timezone: Asia/Novosibirsk
  period:
    start: 2026-07-01
    finish: 2026-07-07
  baseline_ref: baseline-2026-07-01
  current_plan_ref: current
  scenario_ref: null
  data_sources:
    - openproject
    - local
  report_version: 1
```

Reports must state when they are calculated against "current plan as loaded"
rather than a historical current-plan snapshot.

Example:

```text
current plan as loaded, actuals up to status_date
```

The implemented `report estimates` comparison is demand-id based and never
adds unlike units. It reports added and removed demands, same-id re-estimates,
finished-only and all-task resource totals, partial actuals on open tasks, and
baseline-versus-actual schedule dates. It counts `work_consumed`,
`consumption` and `runtime_consumed` actuals in the demand's unit. Actual dates
come first from status audit records that explicitly retain the new status and
status date, then from consumption actual dates; historical audit rows without
those facts are not inferred. Added resources get a separate split comparison
against the largest same-task, same-unit reduction, falling back to the task's
baseline unit total. Resource split groups combine the complete original and
split-out resource rows, while resources without any counted actual are marked
`actuals_recorded: false` and excluded from those combined values. Summed and
derived result numbers are rounded to six decimal places without changing raw
canonical records.

## Weekly report

The weekly report is the primary human planning report.

It should answer:

```text
what changed;
what is overloaded;
what is blocked;
what is at deadline risk;
what actuals are missing;
what decisions are needed;
what evidence/proposals need review.
```

Required sections:

- report metadata;
- executive summary;
- task status summary;
- baseline/current/actual/forecast summary;
- resource workload summary;
- overloads and shortages;
- deadline risks;
- dependency risks;
- unscheduled required work;
- missing estimates;
- missing actuals;
- stale progress;
- blocked tasks;
- review-ready tasks;
- accepted tasks with warnings;
- open proposals;
- evidence waiting for review;
- scenario recommendations or active scenarios;
- decisions needed.

Implemented MVP dependency risk surface:

- weekly report includes dependency planning warnings emitted by validation;
- current implemented warning codes are
  `required_dependency_unresolved`,
  `dependency_predecessor_finish_unknown`,
  `dependency_successor_start_unknown`,
  `dependency_successor_starts_before_predecessor_finish` and
  `dependency_blocks_active_successor`;
- weekly report does not automatically reschedule tasks or create proposals from
  these warnings.

## Weekly report summary

The executive summary should be short and decision-oriented.

Example:

```text
Weekly report, status date 2026-07-06

Summary:
  tasks in scope: 42
  in progress: 8
  blocked: 3
  review ready: 4
  accepted this period: 6
  required warnings: 12
  open proposals: 7
  deadline risks: 2
  overloaded resources: 3
```

## Task status summary

Task status summary should use RePlan tracking statuses.

Required groups:

```text
not_started
ready
in_progress
blocked
review_ready
accepted
cancelled
```

It may also show source status mismatch counts.

Example:

```text
Task status:
  not_started: 12
  ready: 7
  in_progress: 8
  blocked: 3
  review_ready: 4
  accepted: 6
  cancelled: 2
  source status mismatches: 5
```

## Baseline/current/actual/forecast summary

Reports should show comparison values when available.

Required fields:

- baseline planned;
- current planned;
- actual;
- remaining;
- forecast;
- variance from baseline;
- capacity shortage where applicable.

Example:

```text
Effort:
  baseline: 120h
  current: 136h
  actual: 48h
  remaining: 92h
  forecast: 140h
  variance: +20h
```

## Resource workload report

Resource workload report should show resource-level load and capacity.

Required sections:

- resource summary;
- daily or period buckets;
- capacity;
- planned load;
- reserved load;
- actual load;
- remaining load;
- forecast load;
- overload;
- underuse;
- unknown capacity;
- warnings.

Example:

```text
Resource dev_ivan
  2026-07-07
    capacity: 8h
    planned load: 10h
    actual: 0h
    overload: 2h
    tasks:
      OP-123: 6h
      OP-124: 4h
```

Resource report must handle non-hour resources:

```text
Resource openai_api_project_quota
  period: 2026-07
    capacity: 10,000,000 tokens
    actual: 4,200,000 tokens
    remaining: 7,100,000 tokens
    forecast: 11,300,000 tokens
    warning: quota forecast exceeds quota by 1,300,000 tokens
```

## Task tracking report

Task tracking report should show execution state.

Required fields:

- task identifier;
- title;
- source system;
- source status;
- RePlan tracking status;
- baseline dates;
- current dates;
- actual start/finish;
- forecast finish;
- demands summary;
- actuals summary;
- remaining work;
- evidence count;
- open proposals;
- warnings;
- decisions needed.

Example:

```text
OP-123 Implement billing adapter
  source status: OpenProject In progress
  tracking status: blocked
  baseline finish: 2026-07-09
  forecast finish: 2026-07-11
  effort: baseline 8h, actual 3h, remaining 7h, forecast 10h
  warnings:
    - forecast exceeds baseline
    - deadline risk
  proposals:
    - proposal-002: move to review_ready
```

## Warnings report

Warnings report should be sortable and filterable by severity, type, task,
resource, demand, scenario and period.

Required warning fields:

- warning identifier;
- type;
- severity;
- target;
- message;
- evidence references;
- proposal references;
- suggested next action when available.

Warning severities:

```text
critical
high
medium
low
info
```

Required warning categories:

- missing data;
- overload;
- shortage;
- conflict;
- deadline risk;
- dependency risk;
- tracking inconsistency;
- proposal pending;
- evidence pending review;
- source mismatch.

## Scenario diff report

Scenario diff report should show the result of scenario calculation and
comparison.

Required sections:

- scenario metadata;
- base reference;
- scenario status;
- explicit changes;
- calculation summary;
- diff against current plan;
- diff against baseline when baseline exists;
- workload delta;
- schedule delta;
- quota delta;
- budget delta;
- deadline risk delta;
- dependency risk delta;
- warnings added;
- warnings removed;
- apply preview;
- decisions needed.

Example:

```text
Scenario: Use Codex for import adapter
Against: current

Changes:
  add AI-agent demand: codex_agents 2 agent_hours
  reduce Ivan remaining effort: -4h
  add reviewer demand: +2h

Impact:
  forecast finish: -1 day
  Ivan overload: removed on 2026-07-08
  OpenAI quota warning: added
```

## Evidence and proposals report

Evidence/proposals report should show pending review and decision items.

Required sections:

- evidence waiting for review;
- proposals by status;
- proposals by type;
- proposals by actor;
- proposals requiring confirmation;
- stale proposals;
- accepted but not applied proposals;
- rejected proposals with reason;
- recent audit decisions.

Example:

```text
Open proposals:
  proposal-002 status_change OP-123 -> review_ready
    created by: agent_coder_1
    evidence: PR #45, CI #991
    requires confirmation: true
```

## JSON output

JSON is the canonical machine-readable output.

It must include:

- report metadata;
- input references;
- calculation mode;
- baseline reference;
- current plan reference;
- scenario reference when applicable;
- task summaries;
- resource summaries;
- demand summaries;
- workload buckets;
- actual summaries;
- forecast values;
- variance values;
- capacity shortage values;
- warnings;
- proposals;
- evidence references;
- decisions needed.

JSON should be stable enough for AI-CLI agents and scripts.

It does not need to be final public API in early MVP, but avoid unnecessary
churn once implementation begins.

## Markdown output

Markdown is the primary human-readable output.

It should:

- be readable in terminal and editors;
- have clear sections;
- keep decision items visible;
- show warning severity;
- include links or references to tasks/evidence/proposals;
- avoid giant unstructured tables when prose lists are clearer.

Markdown should be generated from the same report model as JSON.

## CSV output

CSV is for table analysis.

CSV should be available for:

- tasks;
- resources;
- demands;
- workload buckets;
- warnings;
- proposals;
- actuals.

CSV does not need to represent nested report structure.

Recommended CSV shape:

```text
one row per object or bucket
stable columns
foreign keys to related objects
```

Example workload CSV columns:

```text
report_id,status_date,resource_id,unit,bucket_start,bucket_finish,capacity,
planned_load,reserved_load,actual_load,remaining_load,forecast_load,overload,
underuse,warnings
```

## Static HTML

Static HTML is useful but not required for MVP core.

Approved rule:

```text
HTML is optional in MVP.
```

Reasons:

- JSON and Markdown are enough for AI-CLI-first operation;
- CSV covers spreadsheet workflows;
- HTML can be generated from the same report model;
- building polished UI too early can distract from the calculation model.

If implemented, static HTML should be a thin rendering layer over JSON report
data.

Implemented weekly HTML slice:

- `replan report weekly --format html` renders a self-contained static HTML
  document to stdout;
- `replan report weekly --format html --write` writes the generated report to
  `reports/weekly/<week>.html`;
- the HTML report includes project metadata, summary metrics, workload rows,
  errors, warnings, open proposals and evidence;
- overloaded resource rows are visually highlighted;
- the HTML report is generated from the same `WeeklyReport` model as JSON,
  Markdown and CSV;
- HTML output is not canonical state and must be regenerated when canonical
  planning data changes;
- no daemon, server runtime, web application framework or client-side
  application state is introduced by this slice.

## Static observability dashboard

The next human observability layer should be a generated static dashboard, not
a live RePlan web application.

Detailed first-slice design is defined in
[`static-observability-dashboard.md`](static-observability-dashboard.md).

Purpose:

```text
make RePlan project state inspectable by a human operator without reading only
CLI JSON, raw YAML or long Markdown reports
```

The dashboard should be generated from existing report and overview models.

It should start as a set of static HTML files:

```text
reports/latest/index.html
reports/latest/weekly.html
reports/latest/workload.html
reports/latest/dependencies.html
reports/latest/warnings.html
reports/latest/proposals.html
reports/latest/raw/*.json
```

Required first-dashboard sections:

- project summary;
- OpenProject import freshness and source health;
- task status summary;
- workload by resource and week;
- overloads and shortages;
- missing estimates, dates and resource demands;
- dependency and deadline warnings;
- blocked or on-hold tasks;
- open proposals;
- accepted actuals and imported actual evidence summary;
- links back to OpenProject work packages when source references are available;
- links to raw JSON artifacts for AI CLI agents and debugging.

Hosting decision:

- first generate locally inside the RePlan project report directory;
- allow opening the HTML directly or through a trivial static file server;
- later publish the same static artifacts read-only on a private host behind a
  reverse proxy with Basic Auth if remote human access is useful;
- do not put this first layer inside OpenProject;
- do not make this a mutating RePlan web application.

Non-goals for this dashboard:

- custom authentication;
- role-based access control;
- live multi-user editing;
- OpenProject write-back;
- background import scheduling;
- daemon requirement;
- replacing OpenProject Gantt, work-package views or collaboration UI.

## Human validation requirements

Every human-facing report should make these visible:

- selected baseline;
- status date;
- unknown values;
- critical warnings;
- blocked tasks;
- deadline risks;
- overloaded resources;
- required demands without capacity;
- required demands without dates;
- required demands without estimates;
- missing actuals;
- open proposals;
- evidence waiting for review;
- scenario changes before applying;
- source status mismatches.

The user should be able to validate:

```text
what RePlan calculated;
what data was missing;
what decision is needed;
why the report says so.
```

## AI-CLI requirements

Reports should support AI agents by exposing:

- structured JSON;
- stable warning identifiers;
- stable proposal identifiers;
- target references;
- evidence references;
- suggested next actions;
- dry-run outputs;
- no hidden UI-only state.

AI agents should be able to:

- inspect warnings;
- create proposals;
- create scenarios;
- summarize decisions needed;
- produce human-readable explanations.

## Candidate CLI commands

Candidate commands:

```bash
replan report weekly --status-date 2026-07-06 --format markdown
replan report weekly --status-date 2026-07-06 --format json
replan report workload --resource dev_ivan --format markdown
replan report warnings --severity high --format json
replan report scenario scenario-001 --against current --format markdown
replan report proposals --status open --format markdown
replan report export workload --format csv
```

Exact CLI design is deferred to `docs/spec/cli.md`.

## MVP requirements

MVP should implement or model:

- weekly report;
- resource workload report;
- task tracking report;
- warnings report;
- scenario diff report;
- evidence/proposals report;
- JSON output;
- Markdown output;
- CSV export for core tabular objects;
- report metadata;
- `status_date`;
- baseline reference;
- current plan reference;
- scenario reference;
- warnings and decisions-needed sections;
- human validation sections;
- AI-CLI-friendly identifiers.

MVP should not require:

- static HTML;
- live dashboard;
- web UI;
- PDF export;
- chart rendering;
- BI integration;
- custom report builder;
- polished executive dashboard.

## Approved decisions

- Reports are a primary RePlan interface.
- JSON is the canonical machine-readable report output.
- Markdown is the primary human-readable output.
- CSV is required for tabular export.
- Static HTML is optional in MVP.
- Weekly report must show status, workload, overloads, shortages, deadline
  risks, missing data, proposals, evidence and decisions needed.
- Scenario report must show explicit changes, calculation results, diffs,
  warning deltas and apply preview.
- Reports must expose enough evidence for human validation.
- Reports must expose enough structure for AI-CLI agents.
- Reports must not hide unknown values.
