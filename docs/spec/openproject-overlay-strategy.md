# OpenProject overlay strategy

Status: accepted direction after the first generated Gantt review.

## Problem

RePlan is designed as a resource-planning layer over a project-management
system, not as a replacement for that system.

OpenProject remains the reference project-management surface for:

- work packages;
- comments;
- human task navigation;
- built-in Gantt;
- relations;
- team collaboration;
- project permissions;
- ordinary project-manager workflow.

RePlan adds a different layer:

- resource demand;
- capacity pressure;
- overload risk;
- non-human resources;
- AI-agent resources;
- quota and environment resources;
- proposals;
- scenario output;
- actual consumption and evidence;
- agent-readable report artifacts.

The first generated `gantt.html` proved that RePlan has enough data to draw a
timeline, but it also exposed a product question: should RePlan keep improving
its own generated Gantt, or should the RePlan layer be shown directly inside
OpenProject?

## Decision

Use a staged hybrid path.

1. Keep RePlan core independent of OpenProject internals.
2. Keep `replan report dashboard` as the first human-observability surface.
3. Improve generated static Gantt enough for dogfood validation.
4. Define OpenProject overlay contracts before building the OpenProject plugin.
5. Build the OpenProject plugin as the OpenProject-specific renderer after the
   overlay contract is stable enough to keep RePlan core PM-agnostic.

This means the immediate implementation path is still the overlay contract and
static generated reports first, then the mandatory read-only OpenProject
plugin.

## Why not start directly with an OpenProject plugin

An OpenProject plugin is attractive because the operator already looks at
OpenProject tasks and Gantt. It is also expensive in the wrong way for this
stage.

Risks:

- OpenProject plugin work couples RePlan to OpenProject internals and version
  details too early;
- browser/UI integration can consume time before the resource-planning model is
  proven;
- plugin authentication, permissions and deployment make the dogfood loop
  heavier;
- OpenProject-specific UI work weakens the universal adapter story for Plane,
  GitHub issues, GitLab issues, Forgejo or other task sources;
- AI CLI agents still need stable CLI/API/raw JSON access rather than a browser
  plugin surface.

OpenProject plugin work should be a distribution/integration layer, not the
core product. The plugin is required for the OpenProject-centered human
workflow, but it must consume RePlan output instead of owning the RePlan model.

## Why keep improving static Gantt

Generated static Gantt is useful when it stays narrow.

It gives:

- deterministic local output;
- no daemon;
- no browser app server;
- no OpenProject write-back;
- no custom auth;
- raw JSON next to HTML;
- easy inspection by humans and AI CLI agents;
- an OSS demo that does not need private infrastructure;
- freedom to show RePlan-specific signals that OpenProject does not know about.

Static Gantt should not become a full MS Project clone.

It should provide:

- readable task timeline;
- status-date line;
- compact status/resource/risk indicators;
- source-system ids and links;
- resource pressure overlay;
- warning and dependency badges;
- raw JSON for deeper inspection.

It should not provide:

- drag-and-drop scheduling;
- browser-side mutation;
- OpenProject write-back;
- multi-user live collaboration;
- full critical-path engine;
- full dependency graph editing;
- full resource-leveling UI.

## OpenProject overlay contract

Before building a plugin, RePlan should stabilize the data contract that an
OpenProject-side overlay would consume.

Required signals:

- RePlan task id;
- source system;
- OpenProject work-package id;
- source URL;
- planned start and planned finish from RePlan;
- OpenProject start and finish from import/comparison when available;
- tracking status;
- assigned resource ids;
- overloaded resource ids;
- resource pressure severity;
- warning codes;
- dependency count;
- open dependency count;
- open proposal flag;
- actual-consumption summary;
- evidence count;
- scenario delta when rendering a scenario.

Potential overlay placements:

- generated static report with OpenProject links;
- OpenProject custom fields populated by a controlled export/write-back step;
- OpenProject work-package comments or attachments generated by a controlled
  export/write-back step;
- external static page linked from OpenProject;
- OpenProject plugin side panel;
- OpenProject Gantt overlay plugin.

The static dashboard remains the PM-agnostic reference renderer, but the real
OpenProject plugin path is now mandatory for a usable OpenProject-centered
human workflow. External static pages and controlled export/write-back remain
useful stepping stones, not substitutes for the plugin.

## Overlay JSON contract

`replan report dashboard` writes `raw/openproject_overlay.json`, the only
input of the OpenProject plugin. Everything in it is derived by RePlan; the
plugin lays it out and does no planning arithmetic.

`schema_version` is 2 since 2026-09-25
(`task.self.extend-overlay-contract-for-plugin-views`). Version 2 keeps every
version 1 field unchanged and adds what the redesigned plugin views draw, as
specified in
[`../dev/openproject-plugin-redesign-design.md`](../dev/openproject-plugin-redesign-design.md).
The plugin reads versions 1 and 2 and shows the reason on both pages for any
other version.

Version 1, project level: `generated_at`, `project_id`, `project_name`,
`status_date`, `week`, `openproject_project_id`, `artifact_refs`, the counts
`work_package_count`, `linked_task_count`, `missing_link_count`, and
`missing_links`.

Version 1, per entry of `work_packages`: `work_package_id`,
`work_package_url`, `replan_task_id`, `title`, `type`, `tracking_status`,
`planned_start`, `planned_finish`, `start_offset_days`, `duration_days`,
`resource_ids`, `overloaded_resource_ids`, `warning_codes` (Gantt signals,
including `dependency_open`), `dependency_count`, `open_dependency_count`,
`has_open_proposal`, `tracking` (actual and evidence counts, flags) and
`resource_demands`, one per demand with its window, amounts, intensity and
flags.

Version 2 adds, at project level:

| Field | Meaning |
|---|---|
| `span` | the plan's date axis: `start_date`, `finish_date`, `day_count`, `status_offset_days`, `status_in_range` |
| `warning_count` | the warnings `replan validate` reports |
| `open_proposal_count` | proposals with status `open` |
| `person_actions` | the next actions of `replan next` that wait on a person: `code`, `label`, `task_id`, `work_package_id`, `date` |
| `resources` | every resource and unit the plan uses: `id`, `name`, `class`, `unit`, `concurrent`, `working_weekdays` (Monday first; absent means every day) and `weeks`, one per ISO week of the span with `capacity` in effect that week, `planned` load and `overload`; for a concurrent resource `planned` is the busiest day |
| `overloaded_weeks` | resource-weeks from the status week on that `replan workload --week` reports as overloaded: `resource_id`, `resource_name`, `unit`, `week`, `capacity`, `load` (remaining or reserved), `overload`; done work does not count |

and per work package:

| Field | Meaning |
|---|---|
| `first_actual_date`, `last_actual_date` | the first and last booked consumption |
| `evidence` | what was done: `id`, `date`, `kind`, `summary`, oldest first |
| `actuals` | booked consumption: `date`, `demand_id`, `resource_id`, `resource_name`, `amount`, `unit`, oldest first |
| `warnings` | `validate` warnings about the task, its demands, or a dependency it waits on: `code`, `message`, `severity`, `target_id` |
| `open_proposals` | open proposals about the task or its demands: `id`, `type`, `target_id`, `rationale` |
| `dependencies` | `direction` (`predecessor` or `successor`), the other task's `task_id`, `task_title`, `work_package_id`, `task_status`, and the dependency's `id`, `status`, `criticality` |

and per resource demand: `resource_name`, `concurrent`, and
`daily_capacity`, the capacity in effect on the window's first working day
for one working day (a week's capacity shared by its working days, or the
number of slots). With `amount_per_day` it gives the lane height the design
draws.

Placement follows the GAP-031 rule shared with `replan workload` and the
dashboard: period demands spread over working days, slots counted by peak.

## Plugin entry criteria

Start OpenProject plugin implementation only when all of these are true:

- static Gantt is understandable enough to show what the RePlan overlay should
  communicate;
- `raw/gantt.json`, `raw/overview.json` and `raw/openproject_overlay.json`
  contain the required overlay signals;
- the OpenProject-centered workflow has confirmed that operators need to see
  RePlan resource pressure while looking at OpenProject work packages;
- OpenProject import/export mapping is stable enough that RePlan task ids and
  work-package ids round-trip predictably;
- plugin scope is limited to read-only overlay or explicitly controlled writes;
- RePlan core remains usable without OpenProject.

## Current implementation state

The accepted first OpenProject-native surface design is documented in
[`../dev/openproject-native-replan-surface-design.md`](../dev/openproject-native-replan-surface-design.md).

Level 0 and Level 1 have been implemented:

- stable links and shared identity between OpenProject work packages and RePlan
  tasks;
- adjacent read-only RePlan dashboard and Gantt-like reports that can be opened
  next to OpenProject;
- raw JSON artifacts with the same overlay signals for AI CLI agents;
- a dedicated `raw/openproject_overlay.json` artifact that future plugin code
  can consume without parsing HTML or recomputing RePlan state.

The plugin path has also advanced beyond the original strategy:

- the read-only OpenProject plugin is mandatory for the OpenProject-centered
  human workflow;
- the minimal plugin consumer has been scaffolded;
- the plugin deployment path has been tested in a throwaway OpenProject
  runtime;
- the plugin has been installed in the private live dogfood OpenProject
  instance;
- the current project-level plugin view renders resource-aware RePlan state
  from `openproject_overlay.json`.

The next active OpenProject-native surface is a read-only work-package-level
RePlan panel. It should still consume overlay artifacts and should not compute
RePlan planning state inside OpenProject.

The next controlled visual target after that is a Gantt-like RePlan view inside
the plugin. True native OpenProject Gantt modification is intentionally later
because it couples RePlan to OpenProject frontend internals and version-specific
behavior.

The completed static Gantt readability work focused on:

- compact task rows;
- no long resource-id overflow;
- tooltips or raw JSON for full ids;
- status-date line;
- date ticks that are readable at day/week scale;
- visual legend;
- status colors;
- compact resource pressure, dependency and warning badges.

Static reports remain the PM-agnostic reference renderer and OSS-friendly demo
surface. They no longer represent the whole human OpenProject workflow by
themselves.
