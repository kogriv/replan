# Static observability dashboard design

Date: 2026-07-20

Status: first implementation slice completed.

## Purpose

The first RePlan human interface beyond CLI, JSON, Markdown and weekly HTML
reports should be a generated static observability dashboard.

Its purpose is to answer:

```text
What is happening in this project now, what is risky, and what should the
operator inspect or decide next?
```

The dashboard is not a project-management system. OpenProject, Plane, GitHub,
GitLab or another task source remains the task collaboration surface. RePlan
adds resource planning, workload, constraints, evidence, proposals and
AI-friendly inspection over that source data.

## Product position

The dashboard is a read-only project state surface.

It is for:

- human validation of RePlan calculations;
- operator triage;
- reviewing overloads and shortages;
- reviewing warnings and missing planning data;
- reviewing dependencies and deadline risk;
- reviewing proposals and evidence;
- checking source synchronization health;
- giving AI CLI agents stable raw artifacts to inspect.

It is not for:

- editing tasks;
- replacing OpenProject work-package views;
- replacing OpenProject Gantt;
- replacing team collaboration;
- replacing TaskJuggler reports;
- creating a live RePlan web application;
- custom authentication;
- role-based access control;
- server-side sessions;
- background imports;
- automatic OpenProject write-back.

## First public input

The first public dashboard design and implementation should use:

```text
examples/replan-self/
```

This keeps the demo public and close to the product:

```text
RePlan is planned with RePlan.
```

Private pilots may validate the same output shape, but private pilot data must
not define the public examples or public screenshots.

## Output mode

The dashboard is generated by a CLI command and then exits.

Approved command shape for first implementation:

```bash
replan report dashboard --project examples/replan-self --output reports/latest --format html
```

Equivalent aliases may be added later, but the first implementation should keep
one obvious command.

The command should:

- read project state from the configured RePlan project directory;
- calculate the same underlying report and overview models used by JSON and
  Markdown commands;
- write deterministic static artifacts;
- avoid any mutation of canonical planning state;
- avoid network calls unless a future explicit import or refresh command is
  invoked separately;
- return a machine-readable JSON envelope when `--format json` is requested.

## Artifact layout

Default output inside a RePlan project:

```text
reports/
  latest/
    index.html
    gantt.html
    workload.html
    tasks.html
    dependencies.html
    warnings.html
    proposals.html
    evidence.html
    sources.html
    scenarios.html
    raw/
      overview.json
      gantt.json
      openproject_overlay.json
      weekly.json
      workload.json
      tasks.json
      dependencies.json
      warnings.json
      proposals.json
      evidence.json
      sources.json
      scenarios.json
      manifest.json
```

The first implementation may start with fewer HTML pages if the index page
contains all required sections, but the raw JSON files should be designed as
separate stable artifacts from the beginning.

`raw/gantt.json` is the stable timeline object for agents and future UI
clients. It contains the planned date range, scheduled tasks, unscheduled
tasks, tracking status, source references, assigned resource ids, overloaded
resource ids, warning codes, dependency counts and open-proposal flags.

`raw/openproject_overlay.json` is the stable OpenProject-facing overlay object
for agents and the future read-only OpenProject plugin. It is organized around
OpenProject-linked work packages and carries the RePlan layer that OpenProject
does not own: RePlan task id, task dates, tracking status, resource demand
rows, participation windows, planned amount, actual amount, remaining amount,
forecast, variance, evidence count, resource load intensity, warning codes,
open dependency count and open-proposal marker.

The overlay artifact is read-only. It is a presentation and inspection
contract, not a mutation log and not a broad bidirectional synchronization
mechanism. Narrow OpenProject write-back remains limited to reviewed helpers
with dry-run by default and explicit apply gates.

Generated files are artifacts, not source of truth.

## Page model

### `index.html`

Primary operator overview.

Required sections:

- project identity;
- status date;
- generation timestamp;
- source snapshot summary;
- health summary;
- top warnings;
- top overloads;
- blocked or waiting work;
- open proposals;
- recent actuals/evidence;
- next actions.

The index page should be enough for the operator to decide where to click next.

### `gantt.html`

Focused read-only timeline view.

This page exists because the table-heavy overview is too hard to compare with
OpenProject Gantt by eye. It should show a familiar project timeline while
adding RePlan-specific resource and planning signals.

Required first slice:

- one row per scheduled task;
- planned start and planned finish rendered as a horizontal bar;
- task title and RePlan task id;
- tracking status;
- OpenProject source id and link when present;
- compact assigned-resource count derived from resource demands;
- compact overloaded-resource count when the selected report week shows
  resource pressure;
- compact warning count for task-level warnings or unresolved dependency
  signals;
- compact open dependency count;
- compact open proposal marker;
- full resource ids, warning codes and source ids retained in HTML tooltips and
  `raw/gantt.json`;
- resource allocation sub-rows under each task;
- resource allocation bars derived from `resource_demands`;
- task date inheritance when a resource demand has no own timing fields;
- `preferred_start`/`preferred_finish` or `earliest_start`/`latest_finish`
  support when a resource demand has its own timing;
- resource allocation horizontal length shown as the participation window, not
  the amount of work;
- resource allocation vertical fill height shown as intensity against matching
  resource capacity;
- aggregated resource load section below the task Gantt with authoritative
  weekly buckets;
- visible one hundred percent capacity waterline in the aggregated resource
  load section;
- overload rendered above the one hundred percent waterline instead of being
  capped or hidden;
- status-date line;
- readable date ticks at day/week scale;
- visual legend;
- separate unscheduled task section for tasks without valid planned dates.

The first Gantt view is intentionally static.

It must not:

- mutate task dates;
- perform drag-and-drop rescheduling;
- write back to OpenProject;
- require live OpenProject access;
- replace the OpenProject Gantt screen.

The purpose is human validation and agent-readable observability. OpenProject
remains the primary project-management surface for work packages, comments,
team collaboration and built-in Gantt. RePlan renders its own focused Gantt
artifact so the operator can see the RePlan resource-pressure layer next to the
source-system schedule.

The first resource allocation slice is intentionally approximate. If a
`ResourceDemand` has no explicit timing, the Gantt allocation row inherits the
task planned start and finish. If timing exists, the generated view uses
`preferred_start`/`preferred_finish` first, then
`earliest_start`/`latest_finish`, then task dates.

The implemented resource visualization design is documented in
[`../dev/dashboard-load-profile-semantics-design.md`](../dev/dashboard-load-profile-semantics-design.md).
The important semantic rule is that resource allocation bars must not encode
planned amount by shortening the bar unless the demand has an explicit timing
window. Horizontal length means participation window. Vertical fill height
means utilization or intensity.

`raw/gantt.json` exposes this explicitly for each task allocation:

- `participation_window_source`;
- `window_capacity`;
- `capacity_known`;
- `intensity_ratio`;
- `intensity_percent`;
- `over_capacity`.

The aggregated resource load section uses authoritative week-level buckets for
the current MVP. `raw/gantt.json` exposes `bucket_type`, `waterline_ratio`,
`max_utilization_ratio` and per-bucket capacity, planned amount, utilization
and overload fields. The HTML graph keeps exact values in tooltips and raw JSON
while making the profile itself the primary signal.

The OpenProject plugin path is documented separately in
[`openproject-overlay-strategy.md`](openproject-overlay-strategy.md).

Current update:

- the generated static dashboard and Gantt remain the PM-agnostic reference
  renderer and OSS-friendly report output;
- `raw/openproject_overlay.json` is also the data contract consumed by the
  OpenProject plugin;
- the read-only OpenProject plugin is already installed in the private
  dogfood OpenProject runtime;
- the project-level plugin view renders resource-aware RePlan state from the
  same overlay artifact family;
- the next OpenProject-native surface is a read-only work-package-level panel;
- native OpenProject Gantt modification remains deferred until simpler plugin
  surfaces prove that the additional OpenProject frontend coupling is worth it.

### `workload.html`

Resource and capacity view.

Required sections:

- workload by resource;
- capacity by unit;
- remaining demand by unit;
- overload amount;
- shortage amount;
- utilization;
- resource class;
- source references when available;
- affected tasks.

It must handle human and non-human resources:

- people;
- AI agents;
- reviewer role;
- CI minutes;
- token quotas;
- local environments;
- release windows;
- equipment or other schedulable resources.

### `tasks.html`

Task state and planning completeness view.

Required sections:

- task id and title;
- source reference;
- tracking status;
- planned dates;
- deadline;
- assignee hint;
- resource demands;
- missing estimate flags;
- missing date flags;
- blocked/on-hold flags;
- dependency count;
- warning count.

### `dependencies.html`

Dependency and deadline risk view.

Required sections:

- dependency graph rows;
- predecessor;
- successor;
- relation type;
- source relation reference when available;
- status;
- blocking risk;
- deadline conflicts;
- unresolved dependency warnings.

This is not a graphical network view in the first slice. A sorted table is
enough if it is easy to inspect.

### `warnings.html`

Validation and planning health view.

Required sections:

- severity;
- diagnostic code;
- object type;
- object id;
- message;
- suggested operator action;
- source reference when available.

Warnings should be stable and deterministic so AI CLI agents can compare them
between runs.

### `proposals.html`

Decision queue view.

Required sections:

- proposal id;
- status;
- proposed by;
- created at;
- affected objects;
- summary of proposed changes;
- expected impact;
- required operator action;
- related evidence.

The dashboard must not accept or reject proposals. It only links to CLI commands
or raw proposal artifacts.

### `evidence.html`

Execution evidence view.

Required sections:

- evidence id;
- source type;
- source reference;
- occurred at;
- linked task;
- linked demand;
- linked actual;
- trust/acceptance status when available.

### `sources.html`

Synchronization health view.

Required sections:

- configured task sources;
- source profile id;
- source type;
- source base URL only if it is safe and already public/sanitized;
- last import snapshot id;
- last import time;
- imported tasks count;
- source references present/missing;
- stale source warnings;
- missing bridge sidecar warnings.

For public examples, use sanitized domains such as `op.example.internal`.

### `scenarios.html`

Scenario inspection view.

Required sections:

- scenario id;
- scenario title;
- status;
- changed assumptions;
- affected resources;
- affected tasks;
- generated diff summary;
- warnings/errors from scenario diff.

The first dashboard does not apply scenarios.

## Raw JSON contracts

The raw JSON artifacts are as important as the HTML.

They should support:

- AI CLI agent inspection;
- deterministic diffs;
- snapshot tests;
- simple external scripts;
- future dashboard clients.

All raw JSON artifacts should include:

```yaml
schema_version: 1
generated_at: timestamp
project_id: string
project_name: string
status_date: date
source_snapshot_refs: list
warnings: list
data: object
```

`manifest.json` should include:

- command;
- RePlan version or commit if available;
- project path;
- status date;
- generated artifact list;
- artifact content hashes when practical;
- warnings count;
- errors count.

## Operator next actions

The dashboard should not only show data. It should surface next actions.

Examples:

- inspect overloaded maintainer capacity;
- review open proposal;
- add missing resource demand;
- resolve unresolved dependency;
- refresh OpenProject import;
- inspect stale source snapshot;
- add accepted actuals;
- run a scenario diff;
- generate TaskJuggler schedule for a selected scenario.

Next actions should be rendered as text and, when useful, as copyable CLI
commands.

## AI CLI friendliness

The dashboard slice must be AI CLI friendly from the beginning.

Requirements:

- deterministic artifact paths;
- deterministic ordering;
- stable diagnostic codes;
- raw JSON beside HTML;
- no hidden writes;
- no browser-only state;
- no network dependency;
- no auth dependency for local generation;
- clear command examples;
- explicit source references;
- explicit object ids;
- explicit status date.

AI agents should be able to answer:

```text
What should I inspect next?
What proposal is awaiting review?
Which resource is overloaded?
Which task lacks a demand?
Which source data is stale?
Which command should I run next?
```

without scraping HTML.

## OpenProject relationship

OpenProject remains the first human PM surface.

The dashboard should link to OpenProject work packages when source references
exist and are safe to render.

The dashboard should not:

- embed OpenProject;
- replace OpenProject Gantt;
- write to OpenProject;
- require OpenProject live access during dashboard generation;
- expose private OpenProject domains in public examples.

For public fixtures, source references should use sanitized or fake values.

## Hosting

First placement:

```text
local RePlan project reports directory
```

The generated HTML should work by opening `index.html` directly from disk.

Later placement:

```text
read-only static publication behind a private reverse proxy
```

Remote publication is optional and should reuse the same static artifacts. It
should not force RePlan to become a daemon or server application.

## Implementation order

Recommended implementation sequence:

1. Add domain/report model for dashboard overview.
2. Add JSON output for dashboard overview.
3. Add `manifest.json` artifact generation.
4. Add single-page `index.html` generated from the overview model.
5. Add raw JSON artifacts under `reports/latest/raw`.
6. Add focused static `gantt.html` and `raw/gantt.json` after the index proves
   too table-heavy for human validation.
7. Add smoke or golden tests for `examples/replan-self`.
8. Add optional static publication documentation later.

## MVP acceptance criteria

The first implementation slice is acceptable when:

- `replan report dashboard --project examples/replan-self --output <dir>`
  generates a dashboard without network access;
- output contains `index.html`;
- output contains `gantt.html`;
- output contains `raw/overview.json`;
- output contains `raw/gantt.json`;
- output contains `raw/openproject_overlay.json`;
- output contains `raw/manifest.json`;
- `index.html` shows project summary, top warnings, top overloads, open
  proposals, dependencies and next actions;
- `gantt.html` shows a read-only timeline with task bars, OpenProject refs and
  RePlan resource/warning badges;
- JSON output is deterministic enough for tests;
- no canonical project files are changed by dashboard generation;
- `./scripts/smoke-mvp.sh` covers at least one dashboard generation path;
- generated dashboard works from a temporary copy of `examples/replan-self`;
- no private domains or private pilot data are required.

Implemented first slice:

- `replan report dashboard` generates a local static dashboard;
- output includes `index.html`, `gantt.html`, `raw/overview.json`,
  `raw/gantt.json`, `raw/openproject_overlay.json` and
  `raw/manifest.json`;
- MVP smoke generates the dashboard from a temporary copy of
  `examples/replan-self`;
- source-health output shows linked OpenProject work-package refs and tasks
  without source links;
- focused Gantt output shows the RePlan timeline and source links without live
  OpenProject access or write-back;
- focused tests cover dashboard HTML rendering and artifact writing.

## Non-goals for first implementation

- live web UI;
- RePlan daemon;
- RePlan server API;
- dashboard login;
- dashboard RBAC;
- OpenProject write-back;
- proposal accept/reject buttons;
- browser-side editing;
- custom charting framework;
- real-time refresh;
- multi-user collaboration.

## Decision summary

- Build the first human observability layer as generated static files.
- Use `examples/replan-self` as the public input.
- Keep HTML read-only and report-driven.
- Keep raw JSON first-class for AI CLI agents.
- Keep OpenProject as the human task/source system.
- Defer daemon, server, auth and mutating UI.
